# S18: Wasm modules in Dynamic Workers

Run on 2026-10-10 against the live edge. Every request below was served from the LHR colo. Code is in [`spikes/18-wasm-loader/`](../../spikes/18-wasm-loader/). Raw results are in `spikes/18-wasm-loader/results/`.

## Answer

**GO for Tier 1, with conditions.** Ruff, clang-format, hcl2json and tree-sitter all load as `{wasm}` modules in a Dynamic Worker with `globalOutbound: null`. All four instantiate and return output byte-identical to Node, and none breaches 128 MB.

Conditions:

1. **No runtime compile.** Wasm has to arrive in the `modules` map. Three of the four glues needed a small adaptation (see [Glue adaptations](#glue-adaptations)).
2. **Warm reuse needs a pinned host.** Reusing the same `id` from a stateless host is unreliable: 1 hit in 6 in one probe. Through a Durable Object it hit 80/80.
3. **Don't read multi-MB wasm from R2 on every cold load.** That read costs 80–840 ms, and with it the cold-start criterion fails for hcl2json and the 10 MiB module.
4. **Hard ceiling of 64 MiB of code per Dynamic Worker.** Padded modules of 10, 30 and 60 MiB all work; 100 MiB is refused.

**Fallback taken:** Ruff (10.9 MB, cold load+run p50 673 ms) runs as a static `keel-verify` Worker. clang-format, hcl2json and tree-sitter run in Tier 1. None of them needs Tier 2.

## Question

Can Wasm tools load as `{wasm}` modules in a Dynamic Worker with `globalOutbound: null`, and up to what size?

- Load Ruff, clang-format, hcl2json and a tree-sitter grammar.
- Load padded modules of about 10, 30 and 60 MB.
- Compare against the same tools in a static Worker.

Pass criteria:
- every module instantiates;
- cold start < 300 ms at ≤ 10 MB;
- memory stays under 128 MB.

Notes on the choices:
- Ruff 0.17.0 was one day old and failed the registry's minimum-release-age policy, so 0.16.10 is used.
- `tree-sitter-wasms@0.1.13` was tried first. Its grammar carries the legacy `dylink` section, and web-tree-sitter 0.27 refuses it (`getDylinkMetadata` → `failIf`). The grammar package's own wasm carries `dylink.0` and works.
- hcl2json comes from the published cdktf build: HashiCorp's Go HCL→JSON bridge, which exposes `parse(filename, contents, cb)`. Building `tmccombs/hcl2json` from source was not needed.

Install-time build scripts for esbuild, workerd and the tree-sitter packages are denied (`pnpm-workspace.yaml` `allowBuilds: false`). No downloaded script was run.

Components:

- **`build/` (gitignored), regenerated by scripts:**
  - `scripts/prepare-wasm.ts` copies each tool's wasm into `build/wasm/` and writes a manifest of sizes and sha256.
  - `scripts/wasm-gen.ts` hand-assembles the padded and probe modules.
    - Padding is a deterministic xorshift stream, so it is incompressible. "MiB" means 2^20 bytes.
    - **active**: one active data segment, copied into linear memory at instantiation.
    - **passive**: the payload stays in the module bytes only.
    - Every module is validated in Node before upload.
- **Children** (`src/children/*.ts`):
  - Each child is one module Worker per tool, bundled by `scripts/build-children.ts` (esbuild 0.28.2).
  - `./*.wasm` and `./*.bin` imports stay external.
  - Wasm is instantiated lazily on the first request, so first-request CPU includes instantiation.
  - The same bundle feeds both the dynamic path and the static path.
- **R2 `keel-spike-18-wasm`:** every blob, uploaded with `wrangler r2 object put --remote` (`scripts/upload.sh`).
- **`keel-spike-18-host`** (`src/host.ts`) has the `LOADER`, R2 and `TOOLS` service bindings, a `ChildTail` tail entrypoint, an `Intercept` loopback, and a `LoaderHost` Durable Object.
  - `/run` calls `LOADER.get(id, cb)`. The callback reads wasm from R2 into `{wasm: ArrayBuffer}`, with `globalOutbound: null`, `limits: {cpuMs: 10000}` and `tails: [ctx.exports.ChildTail({props:{id}})]`. The host times it: `r2Ms` covers the callback's R2 reads; `loadAndRunMs` is the total minus `r2Ms`.
  - `repeat=N` calls the same stub N−1 more times inside one request.
  - `/do-run` runs the same code inside the `LoaderHost` Durable Object.
  - `/static` calls the static Worker over its service binding.
  - Tail events (`outcome`, `cpuTime`, `wallTime`) are written to R2 and read back by the bench.
- **`keel-spike-18-tools`** (`src/tools.ts`): the same child bundles as one static Worker. wrangler resolves `.wasm` imports as CompiledWasm. `tail_consumers` points at the host.
- **`keel-spike-18-static-pad`**: a static Worker holding one padded module, used to see what `wrangler deploy` accepts.
- **Inputs:**
  - `fixtures/sample.py`: Ruff `check` + `format`;
  - `sample.c`: clang-format, LLVM style;
  - `main.tf`: hcl2json;
  - `sample.ts`: tree-sitter parse, counting function-like nodes.

  `scripts/reference.ts` runs the same tools in Node 22 through each package's normal Node entry, which reads bytes from disk and compiles at runtime. It writes `results/reference.json`. Edge output is compared to it as canonical JSON.

source <cf.env>; ./scripts/upload.sh

Measurement caveat: inside a Worker, `Date.now()` advances only at I/O boundaries.
- Calls to a Dynamic Worker child from the plain host advance the clock, at about 10–16 ms per warm call.
- Calls inside the Durable Object, and service-binding calls to the static Worker, often show **0 ms**.

So for warm comparisons, the robust numbers are the **tail `cpuTime`** and the client RTT.

**Ceiling:** total module size per Dynamic Worker is **64 MiB** (67,108,864 B: wasm plus JS). Every load at or below 60 MiB worked. A second limit is the host's own 128 MB: it must hold the bytes as an `ArrayBuffer`, so a 200 MiB blob fails before the loader is reached.

Tail `cpuTime` is 0 ms for passive modules of every size. So **compiling a Dynamic Worker's modules is not billed to the request's tail CPU**, and the cold CPU figures above understate the platform's work. The wall times include it.

## Results: memory

Probes ran through the Durable Object, so a repeat call with the same id reaches the same isolate. `invocation` counts requests served by the child isolate; 1 means a fresh isolate. Raw data: `results/memory-tails.json`.

| Probe | Result | Tail outcome |
|---|---|---|
| One memory, grown 1 MiB at a time and every page touched | reaches 255.06 MiB; `memory.grow` to 256.06 MiB returns −1; the request completes | ok (CPU 272 ms) |
| Hold 208 MiB in module scope, 5 calls, same id | every call finds a fresh isolate (`invocation: 1`, host `cold: true`) | ok ×5 |
| Control: hold 96 MiB, 4 calls | isolate reused (`invocation` 1, 2, 3, 4) | ok ×4 |
| Control: hold 32 MiB, 5 calls | isolate reused (`invocation` 1…5) | ok ×5 |
| 2 memories × 200 MiB in one request | host gets `Error: Worker exceeded memory limit.` | **exceededMemory** |
| 3 or 4 memories × 200 MiB | same error | **exceededMemory** |
| Control: 2 memories × 120 MiB | ok | ok |

```
m7-inst2      exceededMemory cpu 159 wall 168 ['Worker exceeded memory limit.']
m7-inst2x120  ok             cpu 164 wall 184 []
m4-do200      ok  (×5, each reply {'invocation': 1, 'startMb': 0.0625, 'finalMb': 208.0625})
m4-do96       ok  (reply invocation 1,2,3,4; startMb 96.0625 on 2..4)
```

What 128 MB means in practice:
- It is **not** a hard fence inside a request. One wasm memory can grow to just under 256 MiB, and the request returns `ok`.
- When an isolate is above 128 MB at the end of a request, it is discarded silently. The next request gets a fresh isolate, and nothing marks the over-limit request.
- A request is killed with `exceededMemory` only somewhere between 240 and 400 MiB of total wasm memory.

So Keel cannot count on the platform to stop a tool at 128 MB, or to report that it went over. Isolate churn (`invocation` resetting) is the only signal.

## Pass/fail

| Criterion | Result | Evidence |
|---|---|---|
| All tools instantiate as `{wasm}` with `globalOutbound: null` | **PASS** | 4/4 tools; 108/108 responses correct against the Node reference; outcome `ok` on every tail event |
| Padded 10 / 30 / 60 MB instantiate | **PASS** | 6/6 variants, probe 5/5 each; ceiling is 64 MiB total code (100 MiB refused) |
| Cold start < 300 ms at ≤ 10 MB | **PARTIAL** | See below |
| Under 128 MB | **PASS** | No tool hit `exceededMemory`; Ruff 5.4 MB and hcl2json 19.4 MB linear memory; Durable Object reuse 20/20 for all four, which would not happen above 128 MB |
| `fetch()` refused with `globalOutbound: null` | **PASS** | error above; the loopback run fetches, so the probe can tell |

| Over-128 MB child gets an exceeded-memory outcome on the edge | **PASS, with a caveat** | `exceededMemory` at ≥ 400 MiB in one request. Between 128 and about 256 MiB the request returns `ok` and the isolate is discarded afterwards |

Cold start < 300 ms at ≤ 10 MB, in detail:

- **With the wasm bytes already in host memory** (load+run), p50 passes for every tool at ≤ 10 MB:
  - clang-format 147 ms; max 179 ms;
  - tree-sitter 128 ms; max 346 ms, 1 of 7 samples over;
  - hcl2json 280 ms; max 363 ms, 1 of 7 over;
  - 10 MiB pad 142–201 ms.
- **Including a per-cold-load R2 read** (as designed), it fails:
  - hcl2json p50 475 ms;
  - 10 MiB pad 365–625 ms;
  - tree-sitter p50 282 ms, 2 of 7 over;
  - clang-format p50 265 ms, 2 of 7 over.
- Ruff (10.9 MB, just over the bound): load+run p50 673 ms, total p50 1114 ms.

## Recommendation per tool

| Tool | Where | Why |
|---|---|---|
| clang-format | **Tier 1 Dynamic Worker** | cold load+run 147 ms p50, warm CPU 5 ms, unmodified factory |
| tree-sitter (+ grammars) | **Tier 1 Dynamic Worker** | cold 128 ms p50; grammars swap in as extra `{wasm}` modules without redeploying anything |
| hcl2json | **Tier 1 Dynamic Worker** | cold 280 ms p50, warm 4 ms CPU |
| Ruff | **Static `keel-verify` Worker** | static cold 266–453 ms against dynamic 814–1694 ms; same warm CPU; Ruff is fixed, trusted code with no outbound use |
| any of these | not Tier 2 | nothing needed a container |

Shape for Tier 1:
- A `LoaderHost` Durable Object owns `LOADER.get`.
- It keeps the tool `ArrayBuffer`s in memory: 10.7 MB for the three Tier 1 tools, so R2 is read once per Durable Object start, not once per cold child.
- It reuses ids per tool version.
- The plain stateless host is not the place to rely on `get(id)`: in one test it hit a warm isolate 1 time in 6.

## Glue adaptations

| Tool | How the glue expects its wasm | Adaptation |
|---|---|---|
| Ruff | `__wbg_init()` fetches `new URL('ruff_wasm_bg.wasm', import.meta.url)` | none: `initSync({ module })` accepts a `WebAssembly.Module` |
| clang-format | ESM entry uses `import source wasmModule from "./clang-format.wasm"` (source-phase import, which esbuild and workerd don't take); `./web` compiles bytes with `WebAssembly.compile` (blocked) | import `clang-format.js`'s `createModule({ wasm: module })` and `clang-format-binding.js`'s `set_wasm` directly; Emscripten's `instantiateSync` skips compiling when it is given a Module |
| hcl2json | Node bridge reads `main.wasm.gz` with `fs`, gunzips, then calls `WebAssembly.instantiate(bytes, go.importObject)` (blocked) | gunzip at build time and upload raw; import `wasm/wasm_exec.js` for `globalThis.Go`; set `globalThis.__parse_terraform_config_wasm__ = {}` before `go.run(new WebAssembly.Instance(module, go.importObject))`; call `parse(file, src, cb)`. `wasm_exec.js` stubs `fs`/`process` itself. The Go runtime parks between requests and warm reuse worked (40/40) |
| tree-sitter | `Parser.init()` fetches `web-tree-sitter.wasm` via `import.meta.url`; `Language.load(bytes\|url)` compiles at runtime | `Parser.init({ instantiateWasm(imports, done) { done(new WebAssembly.Instance(runtime, imports), runtime) } })` and `Language.loadSync(grammarModule)` (0.27 API, reads `dylink.0` through `WebAssembly.Module.customSections`). Workers expose `process.versions.node` (`22.19.0`) even without `nodejs_compat`, so Emscripten's sniff picks its Node branch; the bundle pins `ENVIRONMENT_IS_NODE = false` (esbuild onLoad patch that fails if the sniff text changes) and aliases `module` and `fs/promises` to a throwing stub. Grammar must be a `dylink.0` build |

Side note: web-tree-sitter keeps a code path that `eval`s JS functions embedded in side modules. The TypeScript grammar never reaches it; a grammar that does would fail in Workers.

## Can-fail demonstrations

1. **Memory:**
   - 2 × 200 MiB gives `exceededMemory`; the control, 2 × 120 MiB, gives `ok`.
   - Holding 208 MiB gives a fresh isolate on every call; the control, 96 MiB, is reused.
2. **Egress:** `globalOutbound: null` throws. The same probe with a loopback `globalOutbound` fetches, so a probe that silently "passed" would show up.
3. **Runtime compile:** the bytes path throws `CompileError … disallowed by embedder`. The same bytes as a `{wasm}` module instantiate and return 42.
4. **Correctness check:** a mutated C input (`return 0;` → `return 1;`) gives `matches reference: False`, and the original gives `True`. The size probe reports `probe ok 0/5` for the refused 100 MiB load.
5. **Warm reuse:** `invocation` counts 1…5 when an isolate is reused and stays at 1 when it is replaced, so the reuse signal is not hard-wired.

## Untested

- Concurrency: 4 concurrent children per Worker request and 10 per Durable Object.
- Enforcement of `limits.cpuMs`: every run used 10,000 ms.
- Colos other than LHR. All numbers come from one client in London.
- Linear-memory size for clang-format and tree-sitter: the glue doesn't expose it.
- Passing a host-side `WebAssembly.Module` (statically imported by the host) into `modules`, instead of R2 bytes.
- Building hcl2json from `tmccombs/hcl2json` with a current Go. The published cdktf build (Go 1.18.5) was used.
- Static Worker size limits between 60 and 100 MiB, and whether the compressed limit differs on other plans.
- Durable Object timing inside the object: `Date.now()` did not advance across child calls, so client RTT and tail CPU stand in for it.
