# S5: K2 as the operations log

**Date:** 2026-10-10. **Code:** [`spikes/05-k2/`](../../spikes/05-k2/). **Raw results:** [`spikes/05-k2/results/`](../../spikes/05-k2/results/).

## Question

Keel's operations and audit log would sit on K2, Cloudflare's durable log on R2 (public beta since 2026-10-01). It is never on the critical path. A Projector DO consumes it, nudged rather than polling.

- Create a stream and a subscription, and record the exact commands, config and binding key.
- Produce 10,000 records from a DO, one at a time and batched. Report produce latency p50/p95/p99, throughput and colo.
- Consume through a nudged alarm loop. Report throughput, end-to-end lag p50/p95, per-entity ordering and duplicates.
- Lease expiry and nack: are un-acked records redelivered after the lease expires, and after how long? Is a nacked record redelivered?

**Pass:** produce p99 < 2 s; consume ≥ 2,000 records/s.

**Fallback:** an `EventLog` backed by Queues plus an R2 archive.

## Answer

- **Produce passes, with a caveat.** Pooled over all 21,478 `send()` calls from DOs: **p50 989, p95 1,223, p99 1,411 ms**, p99.9 2,107 ms, max 2,749 ms. Seven of the eight gated runs pass p99 < 2 s on their own. One fails: `backlog-b1000`, where one of 20 calls took 2,749 ms, and with n = 20 the p99 is that call.
- **Every `send()` costs a fixed ~500 ms** (p50 501–511 ms from LHR, AMS, ATL, SEA and NRT; min ~395 ms), whatever the batch size. One in-order sender of single records manages 2 records/s; 1,000-record batches reach 1,490 records/s.
- **Consume passes only with large pulls.** A nudged projector drained 30,007 records at **4,454 records/s with `max_records: 10,000`**, but only **1,108 records/s with 1,000**: every consume call costs ~0.7 s.
- **Order and duplicates are clean.** There were **0 duplicates and 0 order violations** across 30,007 drained records and 10,000 consumed live.
- **Live lag** (50 concurrent in-order producers, a nudge after every send): produce → consume **p50 1,836 ms, p95 2,205 ms**.
- **Lease and nack behave as documented.** Un-acked records came back to another worker **871 ms after the 5-minute lease ended**. A nacked one-record batch came back **367 ms** after the nack. Two catches:
  - ack and nack are per batch;
  - an ack from a worker that does not hold the lease succeeds.
- **The K2 Worker binding is produce-only.** Consume, subscriptions, ack and nack are HTTP and need an account API token with K2 Consume. wrangler's OAuth login is refused (10210). Keel's Projector needs that token as a Worker secret.
- **Go/no-go: GO for K2 as the ops/audit log, with conditions** (see [Go / no-go](#go--no-go)):
  - each producing DO writes to an outbox and flushes it to K2 in batches from an alarm;
  - the Projector pulls with `max_records: 10,000`;
  - the consume token is handled as a privileged secret.
- **The fallback is measured and stays armed.** Queues produce is ~13× faster (p50 37 ms), but it **does not keep order** (1,055 gaps and 3,283 regressions in 11,000 messages). The R2 archive half is untested.

### What the latency is

- **There is a ~400–500 ms floor per `send()`, whatever the batch size and wherever the producer is.** p50 is 501–511 ms from five colos on three continents, with a minimum of 395–398 ms. A batch of 1,000 records costs the same as one record.
- **It is the durable commit, not the network.** Rejected sends (bad input) come back in **11–14 ms** from the same DO ([`results/send-error-probes.json`](../../spikes/05-k2/results/send-error-probes.json)). The front door is near; the ~500 ms is the time to make the append durable.
- **Concurrent sends from one DO queue behind each other.** With 50 lanes in one DO, p50 doubles to 1,024 ms: the histogram centres on 1,000–1,099 ms, about two commit cycles (`node scripts/histo.ts single10k`). This is **local to the sending DO**. The sequential `seq1k` producer, a different DO on the same stream, ran during the 50-lane run with p50 **505 ms** (n = 390), against **504 ms** (n = 445) after all other load stopped.
- **Batching is what buys throughput.** It runs from 2 rec/s for one in-order sender of singles to 1,490 rec/s at 1,000 per call. 10 lanes × 100 per call reach 1,296 rec/s, and the slowest calls in that run finished together at exactly 1,246 ms, which looks like a shared commit.

## Consume

**The K2 Worker binding is produce-only.** `wrangler types` gives it a single method, `send()`. Consuming is HTTP against the stream endpoint with an account API token holding **K2 Consume**. This was re-checked against the K2 [Consume records](https://developers.cloudflare.com/k2/features/consume/) page (last updated 6 Oct 2026). Keel's Projector therefore needs that token as a Worker secret. Here it was `K2_CONSUME_TOKEN`, set with `printf %s "$K2_CONSUME_TOKEN" | wrangler secret put K2_CONSUME_TOKEN` and never printed. The token has K2 Consume only.

### The nudged alarm loop (`Projector` in `src/index.ts`)

- `nudge()` arms `setAlarm(Date.now())` only if `getAlarm()` is null. It is idempotent: nudges while an alarm is pending cost one storage read.
- Each `alarm()` makes one `POST /subscriptions/<id>/consume` with `{ worker_id, max_records }`. It decodes the records, runs the per-entity checker (`src/check.ts`: `dup`, `regress`, `gap`), writes one row per record, then `POST …/batches/<batch_id>/ack`.
- It **re-arms only if the pull returned records.** An empty pull (`batch_id: null`) ends the loop until the next nudge. A retryable error (10211, 10214, 10216, 10217) re-arms after 1 s.
- One `worker_id` per projector, so one lease at a time and stream order within the subscription.
- Subscriptions were created through the Worker's `/k2/subscriptions` pass-through (`scripts/consume.ts`): `{ "name": "keel-spike-05-<name>", "start_at": { "type": "earliest" } }` → `200 { "result": { "id": … } }`, in 58 ms at K2.

- **A consume call costs ~0.7 s even for 1,000 records.** At 1,000 per pull the loop is bound by that latency, and fails the 2,000 records/s bar.
- At 10,000 per pull (the API maximum; 10 MB response cap; these batches were ~5 MB) one call returns 10,000 records in ~1.6 s, and the loop runs at 4,454 records/s.
- Re-arming the alarm adds only ~25 ms per batch.
- **Per-entity order held, with no duplicates,** across 30,007 records from 50 entities. They were written by 10 concurrent lanes and 1,000-record batches. Every entity's `seq` ran 1, 2, 3, … with no gap.

### Live lag: produce while the projector consumes (`results/consume-lag.json`)

Setup:
- A `latest` subscription and the projector are set up first; the projector accepts the first `seq` it sees per entity.
- Producer DO `p` (AMS) then sends 10,000 single-record batches from 50 in-order lanes, and **after every successful `send()` calls `projector.nudge()`** over DO RPC.
- The projector (LHR) pulls with `max_records: 1,000`.

| Metric | Value |
|---|---|
| Records consumed / unique | 10,000 / 10,000: **0 duplicates** |
| **Order findings** | **none.** 50 entities, written concurrently, each in order. |
| Nudges / alarms armed by a nudge / alarms run / empty pulls | 10,000 / 288 / 290 / 87 |
| Batches | 203, p50 50 records: one commit's worth from 50 lanes |
| `consume` call | p50 696, p95 906, max 1,062 ms |
| **Produce → consume** (record `at` → projector receive) | **p50 1,836, p95 2,205**, p99 2,550, max 2,957 ms |
| … produce → K2 `timestamp_ms` | p50 957, p95 1,114 ms (the `send()` commit under 50 lanes) |
| … K2 `timestamp_ms` → projector receive | p50 880, p95 1,177 ms (mostly the ~0.7 s consume call) |

How the nudge behaves:
- **Nudges coalesce.** 10,000 nudges armed only 288 alarms, because a nudge that finds an alarm pending does nothing.
- **The loop stops when it catches up and restarts on the next nudge.** It went idle 87 times; each time, the next nudge restarted it, and nothing was missed.

The lag spans three clocks: AMS DO, LHR DO and K2. Cloudflare machine clocks are NTP-disciplined, so treat the split as ±tens of ms, not exact.


### Lease, nack and acknowledgement semantics

Probes on `latest` subscriptions, each fed 3 fresh records from producer DO `p-probe`, through the Worker's pass-through. The script is `scripts/lease.ts` and the data is `results/lease-*.json`. IDs are aliased per file.

**Nack** (`lease-nack.json`):

| Step | Result |
|---|---|
| `w1` consume, `max_records: 1` | 1 record, batch A, lease of 300 s |
| `w1` consumes again while holding A | **the same batch A**, lease pushed out by 443 ms (the documented recovery path) |
| `w2` consume, `max_records: 10`, while `w1` holds A | the other 2 records, batch B. A's record is not double-leased. |
| `w1` **nack** A | 200 in 50 ms |
| `w3` consume | **the nacked record again, in a new batch C, 367 ms after the nack** |
| `extend` from a worker that does not hold the lease | **409, 10218** "Lease is no longer held by this worker" |
| `extend` from the holder | 200, new `leased_until_ms` 300 s out |
| **`ack` from a worker that does not hold the lease** | **200, and it really acks:** the holder's next consume returned an empty batch |
| `ack` of an unknown batch ID (32 zeros) | 200 success |

So a nacked "record" (a one-record batch) is redelivered immediately to the next caller. Ack does not check `worker_id`, which matches the docs' "unlike ack and nack" wording for extend. Any holder of the consume token can ack any batch.

**Lease expiry** (`lease-expiry.json`):

| Step | Result |
|---|---|
| `w1` consume, `max_records: 10`, then never ack | 3 records, batch A. `leased_until_ms` − local pull time = **300,757 ms** (a 5-minute lease) |
| `w2` consume straight away | empty (`batch_id: null`). Leased records are not handed to another worker. |
| `w2` polls every 1 s from 15 s before expiry | records reappear on poll 11, **871 ms after `leased_until_ms`** and 301.6 s after the original pull: **the same 3 records, in a new batch** |
| `w1` acks the expired batch A late | 200 success, but **no effect**. `w2` consuming again gets its redelivered batch back, unchanged. |
| `w2` acks, then a final consume | empty |

Redelivery after lease expiry is prompt: within about 1 s of the lease end, at 1 s polling resolution, across two clocks (K2's `leased_until_ms` and the local machine). Un-acked records are not lost, and a late ack from the former holder cannot drop the new holder's lease.

## Can-fail demonstrations

1. **The ordering and duplicate checker fires on bad input, offline** ([`results/canfail-checker.txt`](../../spikes/05-k2/results/canfail-checker.txt)). `scripts/canfail-checker.ts` runs `src/check.ts`, the function the projector uses, over a clean 10,000-record interleaved stream and four corrupted copies:

   ```
   ok   clean             records=10000 findings={} (want 0 findings)
   ok   shuffled          records=10000 findings={"gap":248,"regress":9703} (want regress and gap findings)
   ok   duplicated x3     records=10003 findings={"dup":3} (want exactly 3 dup findings)
   ok   adjacent swap x1  records=10000 findings={"gap":1,"regress":1} (want 1 gap + 1 regress)
   ok   dropped x1        records=9999 findings={"gap":1} (want exactly 1 gap)
   exit=0
   ```

   The harness can fail too. With duplicate detection disabled in `src/check.ts`, the "duplicated x3" case goes red (`FAIL … findings={"regress":3}`, exit 1). The duplicates still surface as regressions, so they cannot pass silently. The file was then restored byte for byte (`cmp`).

2. **The same checker fires live, inside the projector, on real K2 batches** (`results/consume-chaos-*.json`). Two projectors read 3 batches of 1,000 from the backlog with the `chaos` option, which corrupts each batch before checking:

   | chaos | records checked | findings |
   |---|---|---|
   | `shuffle` (Fisher–Yates within each batch) | 3,000 | **385 gap, 2,452 regress** |
   | `dup` (append a copy of each batch's first record) | 3,003 | **exactly 3 dup** |

   The same backlog with `chaos: none` gave 0 findings (`drain`, `drain10k`).

3. **The produce p99 gate goes red at a 1 ms threshold.** `node scripts/gates.ts --produce-p99-ms 1` reports `FAIL` for all 8 runs and exits 1.
4. **The consume gate goes red at an unreachable rate.** `node scripts/gates.ts --consume-rps 1000000` reports `FAIL` for both drains and exits 1.
5. **The 2 s gate already fails for real** on `backlog-b1000` and on the 1,000-record drain, as shown above.

## Go / no-go

**GO: K2 is Keel's operations/audit log**, under these conditions. Each one answers a measured number.

1. **Producers never `await` K2 on a request path.** A `send()` costs ~0.5 s, ~1 s with concurrent sends from one DO, and occasionally 2–2.7 s. Each producing DO writes its op records to a SQLite **outbox** in the same transaction as the state change. An alarm then flushes the outbox in one `send()`, with one send in flight per DO. After a successful send the DO **nudges the Projector**, and only then deletes the rows. That makes the nudge as durable as the outbox: a lost nudge is retried with the flush, and a retried flush can duplicate records, which the projector absorbs.
2. **The Projector pulls with `max_records: 10,000`, one `worker_id`.** Order holds and the drain rate is ~4,450 records/s. At 1,000 per pull it is 1,108 records/s, below the bar. Parallel pulls would need several `worker_id`s, and K2 does not order across workers. The Projector applies a batch, dedupes by record `id` (or `(entity, seq)`), and **acks after applying**.
3. **The consume token is a privileged secret.** It is an account API token with K2 Consume, held by the Projector's Worker only. Any holder can ack **any** batch, whoever leased it. It needs a rotation runbook, and minting it is an owner action.
4. **One stream per environment, not per repo or tenant.** The account allows 20 streams, and names are `keel_*` with underscores. Retention is at most 30 days, so long-term audit history belongs in Keel's own store or R2, written by the Projector, not in K2.

**Fallback (armed, not taken):** an `EventLog` port with a Queues adapter plus an R2 archive.
- **What was measured:** the Queues half produces 13× faster and delivered every message exactly once here.
- **What it would need:** it does not keep per-entity order, so the projector would need a reorder buffer keyed on `seq`, and Queues has no replay, so the R2 archive becomes the only history.
- **What is untested:** the R2 archive.
- **When to take it:** if K2's produce tail grows past the outbox flush budget, or the beta's 10 GB per-account storage cap binds.

**What stays open:**
- K2 under Keel's real shape: many producer DOs, one stream, sustained hours.
- The 10 GB beta storage cap at 30-day retention.
- Billing once enabled: $0.04/GB produced, $0.04/GB consumed, $0.02/GB-month.
- Running the Projector with `max_records: 10,000` under a large live backlog instead of a drain.

## Gotchas

1. **Stream names allow only letters, digits and underscores.** `keel-spike-05-ops` is refused with 10204 "Entity name must be alphanumeric and contain only underscores". Subscription names do allow hyphens. Keel's `keel-*` naming has to become `keel_*` for streams.
2. **The binding takes the stream ID, not the name.** `"k2": [{ "binding": "OPS", "stream": "<32-hex id>" }]`. The ID only exists after `streams create`, so config needs a substitution step (`scripts/deploy.sh`). Deploy validates the binding (codes 10399–10402).
3. **wrangler covers streams only.** `wrangler k2 streams create|get|list|delete` exist. There is no stream update (that is REST `PATCH`), and no subscription, consume, ack or nack command.
4. **Consume is a separate plane with a separate credential.** It lives at `https://<stream-id>.k2.cloudflarestorage.com` and needs an account API token with **K2 Consume**. The wrangler OAuth login, even with `k2.read`/`k2.write`, is refused there with **10210 Permission denied** ([`results/auth-probes.txt`](../../spikes/05-k2/results/auth-probes.txt)). There is no consume binding, so the Projector holds a long-lived account token as a Worker secret, and that token has to be minted and rotated.
5. **K2 cannot push.** There is no K2 event source for Queues subscriptions ([`results/queue-sources.txt`](../../spikes/05-k2/results/queue-sources.txt)) and no consumer binding. A consumer either polls or is nudged by the producer. A lost nudge is only recovered by the next nudge, unless the projector keeps a slow safety alarm.
6. **Every `send()` costs ~400–500 ms**, independent of batch size and region, and concurrent sends from one DO queue to ~1 s. Never `await` K2 on a request path.
7. **`send()` returns no offset or record ID, and never throws on bad input.** It returns `{ success: false, error: { code, message, retryable } }`, so callers must check `success`. A retried batch after an unknown-outcome failure (10212) can be stored twice; K2 does not deduplicate.
8. **HTTP produce on a stream with the HTTP input off returns 404 "Stream does not exist"** (10200), not "input disabled". The wrangler default is HTTP input off.
9. **Ack and nack are per batch, not per record.** "Nack one record" is only possible by leasing a batch of exactly one (`max_records: 1`).
10. **Limits that shape Keel:** 20 streams per account and 10 GB stored per account during the beta. Retention is 1 hour to 30 days. A subscription that falls behind retention silently loses records.

11. **A consume call costs ~0.7 s whatever its size up to ~5 MB**: p50 741 ms for 1,000 records and ~1.6 s for 10,000. An empty pull costs a call too. Throughput comes from big pulls, not fast ones.
12. **Ack does not check `worker_id`.** An ack from a worker that does not hold the lease returns 200 and really acknowledges the batch. Ack of an unknown batch ID also returns 200. Only `extend` checks the holder (409 / 10218). A late ack from a holder whose lease expired is harmless: it returns 200 and the redelivered batch keeps its lease.
13. **Re-requesting while holding a lease returns the same batch** and refreshes the lease. A projector that crashes between consume and ack gets its batch back on restart, under the same `worker_id`.
14. **Subscriptions are immutable and live on the stream.** Deleting the stream removes them. A `latest` subscription starts after the newest record at creation time.
15. **Teardown order matters.** A Worker that consumes a queue cannot be deleted (10064), and a queue still bound by a Worker cannot be deleted (11005). The order is: `queues consumer remove`, then `wrangler delete`, then `queues delete`. A deleted stream's name can be reused at once.
16. **Clocks.** K2 stamps `timestamp_ms` at receipt, which under concurrent load is up to ~1 s after the producer built the record. It cannot be overridden. Use the producer's own `at` for audit time.
