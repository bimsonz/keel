### Added

- **A step command can name a JUnit XML report, and its fail cites the tests the report says failed** (additive: the flow file's `run` gains one optional field, and the command's runner protocol one optional marker). `run: { "command": "…", "report": { "junit": "<path>" } }` names the file the command writes, by a relative path inside the repository (`[A-Za-z0-9_./-]`, no empty, `.` or `..` segment, at most 256 characters); the flow file refuses any other, naming the step. The report rides on the plan step, so the plan's hash covers it. After the command, the runner prints the file gzipped and base64'd as `KEEL_REPORT`, or `KEEL_REPORT none missing` (no regular file there; a link counts as none) or `none too-large` (over 4 MiB), and removes it. The step is still judged by its exit alone; on a fail, its evidence gains `failing`, each `<testcase>` holding a `<failure>` or an `<error>` by its `file` attribute (else its `classname`) and its `name`, the first 50, so the bounce and its remedy's `failingTests` name them as the vitest suite's do. A fail whose report is missing, too large, unreadable or names no failing test says so in its why. vitest (`--reporter=junit`), pytest (`--junitxml`), go-junit-report and cargo-nextest all write the format.
